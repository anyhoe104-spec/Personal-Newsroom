# Personal-Newsroom 要件定義書

## 1. 目的

Personal-Newsroom は、個人の関心テーマに沿ったニュースを毎日自動収集し、スマートフォンで短時間に確認できる静的ニュースアプリとして提供する。

MVPでは、RSSを中心にニュースを取得し、カテゴリ別に10件ずつ表示する。AI要約・日本語化・スコアリング・フィードバックを組み合わせ、毎朝の情報収集に使える状態を目指す。

## 2. 対象ユーザー

- 自分専用のニュースダッシュボードを使いたい個人
- 経済・ビジネス、スイーツ・飲食、AI・活用、卵加工品/卵関連産業の情報をまとめて追いたい利用者
- PCで設定し、スマートフォンで閲覧する運用を想定する利用者

## 3. 対象カテゴリ

| カテゴリ | 目的 | 主な収集対象 |
| --- | --- | --- |
| 経済・ビジネス | 経営判断、事業開発、市場変化の把握 | 経済ニュース、ビジネス媒体、戦略/市場記事 |
| スイーツ・飲食 | 外食・スイーツ・新商品トレンドの把握 | 飲食ニュース、限定商品、店舗/メニュー情報 |
| AI・活用 | AIモデル、開発ツール、API、開発ワークフローの把握 | OpenAI、Google AI、Hacker News、生成AI関連RSS |
| 卵・食品開発 | 卵加工品を軸に、食品業界の商品開発・共同開発・コラボ・製法・素材設計を把握 | 卵、鶏卵、ゆで卵、温泉卵、煮卵、卵加工、食品の商品開発、開発背景、共同開発、コラボ、業務用食品 |

## 4. 機能要件

### 4.1 ニュース取得

- `config/sources.yaml` の `categories.*.sources` を正とする。
- 各ソースは `name`、`source_type`、`url` を持つ。
- `source_type` は `rss`、`google_alert`、`api_stub` を扱う。
- 旧形式のトップレベル `sources` が残っていても、カテゴリ指定があれば互換的に読み込む。
- RSS取得に失敗したソースがあっても、他ソースの処理を継続する。

### 4.2 記事正規化

- 各記事に以下のフィールドを持たせる。
  - `id`
  - `title`
  - `original_title`
  - `display_title`
  - `translated_title`
  - `translated_summary`
  - `fallback_title`
  - `url`
  - `source`
  - `source_type`
  - `source_region`
  - `category`
  - `category_label`
  - `published_at`
  - `raw_summary`
  - `summary`
  - `impact`
  - `egg_insight`
  - `score`

### 4.3 AI・活用カテゴリの日本語化

- AI・活用カテゴリでは、英語記事を日本語タイトル・日本語要約に変換する。
- Anthropic APIキーがある場合は Claude Haiku 系モデルで最終表示候補を一括翻訳する。
- APIキーがない場合や翻訳品質が不十分な場合は、原文タイトルとフォールバック要約を表示する。
- 汎用タイトル、英語のままの要約、原文URLやラベル混入などは翻訳成功扱いにしない。
- 翻訳対象と表示対象の一致は Actions ログで確認できるようにする。

### 4.4 スコアリング

- スコアはキーワード、ソース、鮮度、フィードバックをもとに算出する。
- カテゴリごとに最大10件を表示する。
- 卵カテゴリは国内8件/海外2件を目安に選定する。
- 卵カテゴリでは、卵関連語が見えない広域食品記事を弱関連として下げる、または除外する。
- 卵カテゴリは、卵専用記事だけでなく、食品業界の商品開発に活かせる開発背景・共同開発・コラボ・素材/製法の記事も対象にする。
- ただし、単なる新商品発売、キャンペーン、値引き、まとめ記事は優先度を下げる。

### 4.5 フィードバック

- ブラウザ上の「いいね」「バッド」は `localStorage` に保存する。
- 次回スコアへ反映したい場合は、同形式のデータを `data/feedback.json` に反映し、`scripts/update_preferences.py` を実行する。
- フィードバック学習はカテゴリ内で行う。

### 4.6 静的サイト生成

- `scripts/build_site.py` は `data/articles.json` から `public/index.html` を生成する。
- GitHub Pages の公開対象は `public/` とする。
- スマートフォンで読みやすいカード型UIを提供する。
- 画面の固定文言は `public/i18n.js` の翻訳キー経由で取得する。デフォルト言語は日本語とする。
- 記事本文（タイトル・要約・impact）は翻訳フックの対象外とし、記事データの値をそのまま表示する。

### 4.8 生成結果検証

- `scripts/validate_newsroom.py` で生成結果を検証する。
- 4カテゴリすべてが10件表示されていない場合はエラーとする。
- 卵カテゴリのfallback過多、AI・活用カテゴリの翻訳不足は警告としてログに出す。
- 警告はActionsを失敗させず、次回のソース改善・翻訳改善の判断材料にする。

### 4.7 GitHub Actions

- `.github/workflows/daily_news.yml` は毎日実行される。
- 実行順は `fetch_rss.py`、`score_articles.py`、`build_site.py` とする。
- `build_site.py` 後に `validate_newsroom.py` を実行し、生成結果を確認する。
- 成功時は Pages artifact をアップロードし、GitHub Pages にデプロイする。
- Actions ログには、RSS取得状況、カテゴリ別表示件数、fallback数、AI翻訳状況を出力する。

## 5. 非機能要件

- APIキーなしでもアプリ生成が完了する。
- 外部RSSの一部失敗で全体処理を止めない。
- ログにはAPIキーなどの秘密情報を出力しない。
- ログは標準 `logging` で出力し、レベルとローテーションを環境変数で制御する。本番既定は `INFO` とし、記事単位の診断ログは `DEBUG` に置く。
- 記事単位で繰り返すログには1実行あたりの上限を設け、抑制した件数を必ず報告する。
- 生成物は GitHub Pages で配信可能な静的ファイルに限定する。
- 設定ファイルと記事データは UTF-8 で管理する。

## 6. MVP完了条件

- 4カテゴリすべてで最大10件の記事が表示される。
- `python scripts/fetch_rss.py`、`python scripts/score_articles.py`、`python scripts/build_site.py` がローカルで完了する。
- GitHub Actions の `build` と `deploy` が成功する。
- AI・活用カテゴリで、翻訳済み記事と原文フォールバック記事の状態がUIとログから判別できる。
- 卵・食品開発カテゴリに、明らかなキャンペーン/値引き/単純な新商品リリースだけの記事が優先表示されにくい。

## 7. 現在の改修方針

2026-06-09 時点では、PR #5 までで Actions の可観測性追加が完了している。次の改修では以下を優先する。

1. ソース設定を `categories.*.sources` に統一する。
2. 旧形式ソースも互換的に読み込み、設定ミスで取得漏れが起きにくくする。
3. 卵カテゴリの関連度判定を追加し、広域食品記事の混入を抑える。
4. AI・活用カテゴリの汎用翻訳タイトルを翻訳成功扱いにしにくくする。
5. 要件定義書を設置し、今後の改修判断の基準にする。
